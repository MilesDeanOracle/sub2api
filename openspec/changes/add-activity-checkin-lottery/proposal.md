# 首调、二充与签到留存增长方案（产品评审稿）

> 后续方向更新：用户已将目标明确为持续 API 消费与留存，计划以消费阶梯替代新增二充权益。最新产品与技术评审稿见 [消费阶梯奖励设计](../add-consumption-milestone-rewards/proposal.md)。本文保留已实施方案的历史说明，不代表新阶梯已上线。

状态：首期基础能力已实施，现金活动默认关闭；奖励金额与预算经运营评审后启用。首期保留轻量签到，常驻抽奖与补签卡的原技术设计见 `design.md`，目前是备选能力资料。

## Why

本次活动要改善三个可测量的结果：新用户注册后完成**第一次成功计费的 API 调用**、完成**第二笔有效的付费余额充值**，以及用户在后续月份仍有真实 API 使用。签到服务于第三个留存目标，单纯提高登录或签到点击次数不算成功。

本项目已支持按注册来源设置新用户初始余额，也有 API Key、使用记录、充值订单和邀请返利。激励必须与这些既有能力协同，避免重复送余额及无上限叠加优惠。

站点运营口径由用户补充：当前基本按 `¥1 充值 -> $1 账户余额`。本方案用 **1:1 账户面值**做活动预算推算；上线前必须读取实际 `balance_recharge_multiplier` 与订单实付/到账快照，不能把该口径误认为人民币与美元的市场汇率。奖励展示为账户余额面值，不宣传现金可提现。

## 产品判断

1. **保留轻量签到，取消参考站点的高额连续奖励和首期补签卡。** 签到是使用习惯的入口，首期只对已完成首调的账户开放发奖；奖励以账户余额面值计，**每人每个自然月硬封顶 15 元等值余额**。封顶是风险上限，不是承诺每月发满 15 元。
2. **首期不做“每充 ¥10 获得一次”常驻抽奖。** 它奖励所有充值，包括原本就会发生的第二笔及后续订单，还鼓励拆单。按当前 1:1 充值面值，最低 `$0.50` 奖品相当于每 ¥10 充值至少 5% 的账户面值回馈；还需叠加现有优惠与高额奖品的期望成本。
3. **先消除首调阻力，再测试奖励。** 新用户看到的是一条简短路径：创建或选择 API Key、复制可运行的最小请求、看到首个成功结果。初始余额为零或不足以完成一次调用时，测试组可提供有上限的试用额度；不同时叠加“首调后现金奖”。
4. **二次充值用一次性权益试验。** 用户完成首笔有效充值并有真实 API 使用后，在适当时机看到“第二次充值权益”；可以试验固定小额奖励或一次抽奖，但同一用户终身只获得一次。首期优先固定奖励，解释简单、成本确定；抽奖只有在实验显示固定奖励有效且有进一步提升空间时才进入第二阶段。

签到、首调试用额度、二充奖励分别记账，并受同一用户及全站活动总预算约束；不能把签到的 15 元上限理解为所有活动奖励的总上限。

## 首期用户流程

### A. 首次调用

- 对象：注册后 7 天内、尚无成功计费 API 调用的新用户；现有用户不追溯。
- 页面：仪表盘显示一个明确的“开始调用”入口，包含密钥、模型、最小请求和结果反馈。已有密钥时跳过创建步骤；错误时显示可操作的修复信息。
- 完成口径：网关在确认成功响应且正常用量落库后，记录该用户首次成功、实际计费金额大于 0 的 API 请求事件。现有 `usage_logs` 没有通用的成功状态字段，且拒绝路径也可写用量，不能只凭 `actual_cost > 0` 判定；使用记录作为核对依据，首调事件按用户唯一。前端点击、请求失败和零成本探测均不算完成。
- 奖励：先不额外发现金。先统计初始余额为零、余额不足、密钥创建失败、请求配置错误等阻力，再决定是否对实验组发放一次性试用额度。若试用额度进入现有余额，必须限制对象、金额、总预算并防重复账号套利。

### B. 第二次充值

- 对象：完成首调、已有第一笔有效付费余额充值的用户。是否要求首调发生在首充前，可由真实数据决定，不人为排除已先充值的用户。
- 触发：首充后有至少一次成功计费调用，且距离首充未超过 30 天；在仪表盘和余额不足场景展示一次性权益，避免全站常驻弹窗。
- 领取：按支付完成时间排列真实付费的余额充值订单，只在**第二笔**已完成 `CNY` 订单上判断并发放一次固定奖励；第三笔不能替代不合格的第二笔。建议试验门槛为首充和二充各至少 `¥50`，且两单之间有成功计费调用；这只是防拆单的候选参数，仍需用订单金额分布验证。排除订阅、兑换码、人工调额及退款订单；如果首充或二充退款，资格与已发奖励进入人工审计策略。
- 奖励金额：不在没有毛利数据时预填 `$` 数值。由单用户可承受获客/留存成本倒推：单次奖励上限、试验总预算、与现有充值优惠/邀请返利叠加后的净毛利必须在活动配置中先通过校验。奖励进入现有余额并记录独立流水。
- 对照：按用户 ID 稳定分组，一组只看到正常充值，一组看到二充权益；以“被分配到组”为分析口径，不只比较实际领奖的人。观察首充后 30 天二充率、支付金额、退款率和扣除奖励后的净毛利。

### C. 签到留存

- 对象：已完成首调的正常账户，包括上线前已有真实计费使用记录的老用户；老用户资格可用历史使用记录做一次性兼容判断，但不计入上线后的“新用户首调”指标。未首调用户仍可看到“完成首次调用后开启签到”的状态，但不产生签到奖励。这样签到定位为首调之后的使用习惯，而非单纯注册领钱。
- 规则：每天最多签到一次，以 `Asia/Shanghai` 自然日和自然月计算；首期不提供补签、随机暴击或充值换补签卡。奖励直接记入现有账户余额并有独立流水；单日重复请求幂等返回已签到。
- 预算：每人每自然月最多发放 **15 元等值账户余额**，按站点当前 1:1 口径对应最多 `$15` 余额面值。建议试运行规则为每天 `$0.10`，连续签到第 7/14/21/28 天各加 `$0.50`；31 天满勤最多 `$5.10`，低于硬上限。这个数值是可调的实验起点，不是从参考站点复制的奖励。服务端发奖前以当月已发流水计算剩余额度，不足时只发剩余额度或不发，绝不突破硬上限。
- 展示：签到日历显示已签到日期、当月已领余额、距月度上限剩余额度及下一连续节点。不要显示“每天可领 15 元”或把 15 元作为保证收益；当月封顶后仍可签到记录习惯，但不再发余额。
- 验证：用稳定用户分组比较“首调后次月仍有成功计费调用的比例”和每周有调用的天数，同时看充值、净毛利及每新增活跃用户的奖励成本。签到次数与页面访问只是过程指标。若只有签到上涨而真实调用不变，应停止现金奖励，保留无奖签到或下线。

## What Changes

首期包含首调引导、首调事件去重记录、二充资格计算、一次性发奖、轻量签到、活动配置与审计。保留现有支付和使用主流程；资格从使用记录及已完成订单读取，余额发奖与奖励流水在一个事务中提交，提交后失效余额缓存。活动默认关闭、可按用户灰度；不修改插件协议。

前端在仪表盘相关区域加入首调任务、二充权益与签到入口；签到弹窗保留月历和连签进度，沿用现有 UI 组件与中英文文案。首期不新增补签页面、奖池、十连或常驻顶栏抽奖按钮。参考截图的签到信息结构可用于视觉设计。

## 成功标准与停用条件

| 目标 | 主指标 | 护栏 |
| --- | --- | --- |
| 首调 | 注册后 7 天内首次成功计费调用率，以及注册至首调的中位时间 | 首调失败率、支持请求量、试用额度成本、重复账号率 |
| 二充 | 首充后 30 天内第二笔有效付费充值率 | 每用户净毛利、退款率、拆单率、奖励总额、与原充值优惠叠加成本 |
| 签到留存 | 首调用户次月仍有成功计费调用的比例、每周有调用的天数 | 签到奖励总额、每新增活跃用户成本、异常多账户率、净毛利 |

上线前记录现状基线及测试组分配口径。实验周期和样本量按现有日均新用户/首充用户数计算，不预设“几天后必然有效”；如果只是提高充值次数却降低净毛利，判定为失败。任一活动达到预算上限、异常账户率或退款阈值时自动停止新奖励，保留已发奖励与审计流水。

## 后续阶段

若签到试验只有点击和回访增加、真实 API 使用没有改善，下一轮可测试“使用型签到”：以当天真实 API 调用为完成条件；也可停发现金，仅保留无奖日历。只有二充固定奖励试验有效且需要提高参与度时，再评估一次性抽奖；奖池期望成本先由预算确定，再设计奖品和概率。

## 待评审数据

- 最近 30/60 天注册用户的 7 日首调率、从注册到首调各步骤的失败分布，以及新用户初始余额的实际配置。
- 首充用户的 30 日二充率、两次充值间的 API 使用、订单金额与币种、优惠叠加、毛利和退款分布。
- 可承担的每新增首调用户成本、每新增二充用户成本，以及活动总预算。
- 首调用户的次月真实调用留存、当前充值倍率和余额使用情况；15 元硬上限下的最坏总成本与试运行 `$5.10` 满勤成本。

这些数据决定试验奖励和门槛。没有数据时可先建设无现金的首调引导与事件口径，二充奖励保持关闭。
