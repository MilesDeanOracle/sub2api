# 签到与常驻抽奖活动技术备选方案（暂不实施）

状态：用户目标包括提高新用户首调、促进第二次充值，以及通过签到增加真实使用留存。首期保留低成本签到，具体规则以同目录 `proposal.md` 为准；本文的高额连续签到、补签卡和每 ¥10 赠抽奖次数仍是备选。尚未批准实施，也不包含代码或数据库变更。

## 1. 原候选功能与边界

为已登录用户提供每日签到、连续签到奖励、补签、充值获取抽奖次数、单抽/十连和中奖记录；管理员可以开关活动、设置规则并查看发奖流水。第一版奖励进入现有用户余额，不新增“赠送额度优先消费”钱包。用户界面参考 codexpert.top 的信息结构和交互，图标、插画及具体样式自行实现，不直接搬用站点资产。

本功能以宿主内的独立活动模块实现。当前 `.s2plugin` 只接受 `openai.oauth.outbound_transport.v1`，其 UI 仅供管理员配置传输插件；把活动改造成可安装插件仍需扩展宿主的用户路由、页面挂载、发奖授权和协议，不能消除上游合并成本。

## 2. 已核实的项目边界

### 2.1 codexpert.top 可见机制（2026-11-18 登录后核对）

| 项目 | 页面可确认的行为 | 证据边界 |
| --- | --- | --- |
| 签到 | 30 天奖励周期；日历显示已签到记录，一条历史记录显示 `+$0.20` | 不能据单条记录认定每天固定发 `$0.20` |
| 连签 | 第 3、7、15、30 天展示 `+$1`、`+$3`、`+$5`、`+$10` | 页面未说明 30 天后如何重置或重复发奖 |
| 补签 | 文案明确“正常签到命中节点时发奖，补签只恢复连签”；每月最多领取 1 张补签卡 | 可补日期范围、卡片有效期未展示 |
| 补签卡条件 | 本月累计充值 `¥150`；或本月充值 `¥100` 且有 2 位有效邀请用户，每人本月充值至少 `¥10` | 只确认页面规则文案，未执行领取 |
| 抽奖 | 奖池展示 `$0.5/$1/$3/$5/$10/$50`；有单抽、十连、剩余次数、累计/今日中奖及中奖记录 | 账号剩余次数为 0，未验证实际中奖或到账 |
| 获得次数 | 充值页快捷金额显示 `¥10 -> 1 次`、`¥20 -> 2 次`等比例；活动弹窗称“单次充值满 10 即可获得一次抽奖机会” | 自定义金额、退款与历史订单的处理未展示 |

奖池权重、幸运暴击概率、基础奖是否恒定、退款撤回规则均未在可访问页面中公开，不能把下面的建议机制称为参考站点的实际后台算法。

### 2.2 本仓库的接入边界

| 能力 | 当前实现 | 对方案的影响 |
| --- | --- | --- |
| 用户认证与限流 | `backend/internal/server/routes/user.go` 的 JWT、用户模式保护、面板限流和审计 | 活动接口复用同一组中间件，不另建认证体系 |
| 支付订单 | `payment_orders` 有 `order_type`、`status`、`pay_amount`、`completed_at`、`refund_amount` 和退款状态；`PaymentOrderCurrency` 从订单支付渠道快照读取币种 | 抽奖次数只从符合条件的余额充值订单核算；支付回调不作为首批接入点 |
| 邀请关系 | `AffiliateService` 管理邀请用户和返利 | 补签卡的有效邀请条件以原始邀请关系及合格订单核算，不把返利金额当充值额 |

| 数据迁移 | 启动时执行按文件名排序、带 SHA-256 校验的前向 SQL 迁移 | 只增新表/索引；实现时再确定未占用的迁移文件名，发布后不得修改 |
| 前端 | Vue 3、`pnpm`、中英文 i18n；用户路由及顶栏已有固定入口 | 新增独立活动视图/弹窗和 API 封装；接入点限于相关路由、顶栏与文案 |

### 2.3 原候选活动规则（已从首期范围移除）

以下是**参考可见页面后为本项目制定的规则草案**，不是对 codexpert.top 隐藏算法的断言。活动默认关闭，管理员确认预算与权重后才允许开启。

- **活动日期**：统一使用 `Asia/Shanghai` 的自然日和自然月。30 天为一个连续签到奖励周期；正常签到跨过第 30 天后从下一个周期的第 1 天计算。断签后连签归零，历史累计次数保留。周期是否重复发阶段奖由配置显式控制，第一版建议可重复，但要先确认预算。
- **签到奖励**：建议普通签到固定 `$0.20`，第 3/7/15/30 天额外发 `$1/$3/$5/$10`。参考站点只验证过一条 `+$0.20` 记录，因此固定基础奖是本项目的选择。幸运暴击保留展示位与配置字段，但默认关闭；启用前必须确定暴击倍数、概率和每日预算。
- **补签卡**：按参考页面的两条充值/邀请条件任选其一，每月最多领 1 张。第一版建议仅能补当前自然月内的过去日期；卡在当月末失效，不跨月结转。补签不发基础奖、不补发历史阶段奖；只修复连签状态，不能给补签日期再签到。
- **抽奖次数**：第一版只处理支付渠道币种为 `CNY` 的已完成余额充值订单，`floor(实付人民币金额 / 10)` 次，每单独立向下取整、不跨订单合并零头。订阅、兑换码、人工充值及活动前订单不赠次。`USD` 等其他支付币种首版不参与，避免暗含汇率假设；日后开放时单独定义币种换算与订单快照。
- **奖池**：沿用六档美元面值，单抽扣 1 次，十连扣 10 次、执行 10 次相同独立抽取，首版不设十连保底。权重采用管理员配置的正整数，总和归一化；**没有已核实的参考权重，实施前必须配置并通过预算校验**，不能默认等概率。中奖金额按现有余额单位入账，前端统一标注为“余额奖励”，不称“赠送额度优先使用”。
- **退款**：以下为本项目建议政策。全额/部分退款成功后，按订单实付金额的未退比例重新计算应得次数，追加差额调整流水；退款待处理期间暂停该用户抽奖。已消耗的次数不自动撤销中奖余额，而是记入次数欠额，后续充值次数先抵欠额；可用次数下限显示为 0。异常高额或强制退款进入人工审计。不同退款状态及币种必须在实现时使用现有订单模型逐一验证。

成本门槛：若普通签到固定 `$0.20` 且四个阶段奖每 30 天重复发放，满勤用户每周期可得 `30 x $0.20 + $1 + $3 + $5 + $10 = $25`，尚未包括抽奖和暴击。用户补充该站点当前充值面值基本为 `¥1 -> $1 账户余额`；在这个运营口径下，每 `¥10` 充值对应的最低 `$0.50` 抽奖奖品是至少 5% 的账户面值回馈，不能按人民币/美元市场汇率误算。管理员启用前仍需核对实际充值倍率、预期活跃人数和充值量，计算奖励预算、期望值和最坏情况上限，并设置单用户/全站预算阈值。

## 3. 模块设计

### 3.1 代码归属与接入点

- 后端业务放在 `backend/internal/service/` 的活动服务及专属规则文件，数据访问放在 `backend/internal/repository/`，HTTP 处理放在 `backend/internal/handler/`；沿用 Ent、Gin 和现有 Wire 依赖组装。活动表对应独立 Ent schema，不修改 `User` 或 `PaymentOrder` schema。
- 用户路由在 `backend/internal/server/routes/user.go` 增加 `/api/v1/activities/...`；管理员路由在 `backend/internal/server/routes/admin.go` 增加活动配置和审计查询。对 `handler.go`、Wire provider set 与生成文件的修改仅用于注册依赖。
- 前端 API 放在 `frontend/src/api/`，签到和抽奖 UI 放在用户业务目录；仅在现有顶栏加入入口和可用状态。管理配置放在独立管理视图，沿用现有 UI 组件和 i18n；不改全局 CSS、Tailwind 配置或基础组件。
- 活动配置存于活动专用表，包含启用状态、时区、规则版本、奖励阶梯、奖池权重和限额。修改规则时生成新版本；已发生的签到、次数和中奖记录保留当时的规则版本与金额快照。

### 3.2 数据模型与唯一约束

| 表（建议名称） | 关键字段及约束 | 用途 |
| --- | --- | --- |
| `activity_campaigns` | 活动类型、规则版本、启用时间、结束时间、配置 JSON、状态 | 管理配置与规则快照；上线时先停用 |
| `activity_checkins` | 用户、活动日、`normal/makeup`、连签值、规则版本；唯一 `(user_id, activity_day)` | 防止同一天重复签到或补签；日历按月份读取 |
| `activity_makeup_cards` | 用户、来源、获取月份、领取/使用状态；来源唯一，每月领取约束 | 记录补签卡来源、领取、消耗；补签仅修复连签，不能重发节点奖 |
| `activity_ticket_ledger` | 用户、来源类型及来源 ID、数量正负值、发生时间；唯一 `(source_type, source_id)`，退款调整的来源 ID 含订单 ID 与稳定退款版本 | 充值入账、单抽/十连扣次、退款调整及人工修正的可追溯流水；净次数可为负，前端可用次数最低显示 0 |
| `activity_draws` | 用户、请求幂等键、批次内序号、奖品、金额、规则版本、随机结果摘要；唯一 `(user_id, request_key, draw_index)` | 单抽或十连的逐次结果；整批以请求键定位并原子提交 |
| `activity_reward_ledger` | 用户、奖励来源、奖励种类、金额、发放状态、余额变动后快照；唯一 `(source_type, source_id, reward_kind)` | 同一次签到可分别发基础奖和节点奖；与余额更新同事务并支持管理员核查 |

金额在业务和数据表中按整数最小单位处理，转换为现有余额字段时严格校验精度与范围；不能以浮点概率或浏览器提供的金额决定奖品。随机抽取在服务端使用密码学安全随机源，按整数权重选奖，记录规则版本。用户与时间维度索引只覆盖实际查询路径，不预先建立宽泛索引。

### 3.3 关键事务

1. **签到**：以活动时区计算服务端“今日”，检查启用状态与唯一约束；写签到记录、计算连签和奖项、写奖励流水并增加余额。并发第二次请求返回“已签到”及当前状态，不能再次发奖。节点奖励只在正常签到且首次命中时发放。
2. **补签**：只能选允许的过去日期；锁定并消耗一张有效补签卡，插入该日签到记录并重算受影响的连签展示。是否允许回填多日、回溯影响范围及重复补签须在规则确认后定稿。补签不发基础奖和历史节点奖，除非产品明确改变此规则。
3. **充值次数**：活动服务按订单 ID 增量核算符合规则的 `COMPLETED` 余额充值订单；先用 `PaymentOrderCurrency` 确认 `CNY`，再按订单 `pay_amount` 算次数，不用计入赠金的 `amount`。`activity_ticket_ledger` 的来源唯一约束保证重试、跨实例或重复读取不重复赠次。限定活动开始后的订单，不追溯历史充值。第一次打开活动页或抽奖前同步核算本人待处理订单；另设小批量后台补偿任务处理未访问活动页的用户。无需首批修改支付回调。
4. **抽奖**：先核算次数，再在一个数据库事务中通过用户级事务锁串行化抽奖，检查可用次数与限额、扣除 1 或 10 次、生成奖项、写抽奖及发奖流水、增加余额。次数扣减流水以抽奖请求键为唯一来源；客户端提交稳定幂等键，超时重试从同一请求键读取完整批次结果，不能再次扣次。奖池配置只有服务端可写，前端展示概率策略由管理员决定。
5. **提交后动作**：余额变动提交成功后失效现有认证/计费余额缓存。缓存失败时记录并重试；数据库事务失败绝不返回“成功”。活动记录与余额更新必须使用同一个事务上下文，避免“显示中奖但未到账”。

退款调整以订单已发次数和退款后应得次数之差记账，不删除原始赠次或抽奖流水。对 `REFUND_REQUESTED`、`REFUNDING`、`REFUND_PENDING` 等状态先暂停抽奖；仅在退款成功、退款金额稳定后调整，失败后解除暂停。部分退款金额在订单中按到账余额单位保存，换算回实付币种时复用现有 `calculateGatewayRefundAmount` 的订单比例与舍入语义，避免把 USD 到账额直接当人民币退款额。

## 4. HTTP 契约草案

| 用户接口 | 说明 |
| --- | --- |
| `GET /api/v1/activities/checkin` | 今日状态、月份日历、连签、阶段奖励和补签进度；服务端返回活动时区及日期 |
| `POST /api/v1/activities/checkin` | 今日签到；无请求金额，由服务端定奖 |
| `POST /api/v1/activities/checkin/makeup` | 指定允许的过去日期补签；提交幂等键 |
| `GET /api/v1/activities/lottery` | 剩余次数、奖池展示、中奖统计与规则摘要 |
| `POST /api/v1/activities/lottery/draw` | `count=1|10` 加幂等键；返回完整奖项批次 |
| `GET /api/v1/activities/lottery/history` | 分页读取本人中奖流水 |

所有用户接口只使用当前认证用户 ID，不接受客户端指定 `user_id`。写接口沿用面板限流并加按用户的活动频率限制；管理员配置修改使用现有管理员鉴权、二次验证与审计。活动停用时只读历史仍可访问，写操作返回明确的停用状态。

## 5. 页面与交互范围

- 顶栏两个入口显示签到可操作状态与剩余抽奖次数；点击进入独立弹窗。移动端允许纵向滚动，不把完整日历硬塞进窄屏。
- 签到弹窗包含当前连续、累计次数、月历、正常/补签/今日状态、阶梯奖励、补签卡获取进度。未达标、已领、可领、已使用及跨月切换均需有明确状态。
- 抽奖弹窗包含奖池、剩余次数、单抽、十连、累计/今日中奖及分页记录。结果由服务端返回，动画只呈现结果；按钮在请求期间防重入，超时后用相同幂等键查询/重试。
- 先复用仓库中的模态框及图标体系，视觉参考截图的信息层级与色彩关系，保持本项目的页面骨架、明暗主题和中英文完整。正式开发前对桌面和移动视口做交互与可访问性检查。

## 6. 原候选高额签到与常驻抽奖的分阶段交付与验收（暂不执行）

1. **规则冻结与数据设计**：确认下节业务规则，形成 OpenSpec proposal/design/tasks；核实支付与退款字段、金额单位及现有缓存失效接口。
2. **签到闭环**：迁移、规则配置、签到/补签事务、用户 API、月历 UI、管理员开关和发奖流水。验证跨日、跨月、时区、断签、并发和重复请求。
3. **抽奖闭环**：订单次数核算与补偿、奖池权重、单抽/十连、历史记录、管理查询。验证重复支付回调、订单重试、退款、并发抽奖、超时重试及十连原子性。
4. **上线与回退**：迁移先行且活动默认关闭；灰度开放给测试用户，核对活动流水、余额和充值订单；再扩大开放。回退先关写入口，保留历史数据和已发余额，不修改已应用迁移。发现错发奖励时走有审计的补偿操作，不能删除流水。

验证门槛：后端活动服务单测、PostgreSQL 事务/唯一约束集成测试、用户与管理员路由测试；前端组件和 API 状态测试；`pnpm` lint/typecheck/test/build；桌面与移动浏览器检查。每次同步上游时重点回归支付履约、退款、余额缓存、认证和前端顶栏。

## 7. 上游更新策略

- 将活动功能保持为独立提交序列，与上游同步使用固定节奏的小批量合并；每次合并先检查迁移文件名、Ent 生成代码、Wire 生成代码、用户/管理员路由和顶栏。不要改写已部署迁移的内容或文件名。
- 活动核心逻辑和表保持专属命名，减少与上游的文本冲突；接入点集中在路由、依赖组装和入口。若上游更改支付/余额契约，先修复适配并回归财务测试，再部署新版本。
- 记录已验证的 Sub2API 上游提交或版本、活动规则版本、迁移清单和回退步骤。升级前备份数据库并在测试环境重放生产迁移；多实例部署先保证所有实例都能识别新表和新代码，再开启活动。

## 8. 若重新启用本方案，实施前待确认

1. 是否接受上面的参考规则草案，尤其是每 30 天重复发阶段奖、固定 `$0.20` 基础奖以及补签卡当月失效。
2. 抽奖六档的**具体权重**、单用户每日/每期上限、全站预算上限；幸运暴击是否首版开启及其权重。参考站点未公开这些数值，不能由页面推断。
