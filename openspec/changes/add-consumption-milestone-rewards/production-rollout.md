# 营销奖励生产发布与故障手册

当前为候选实现；不得把本地测试当作生产发布许可。所有命令须先在恢复的生产副本执行。

## 发布前

1. 记录当前应用版本、数据库迁移版本、用户规模、峰值写入及任务积压。备份数据库并验证独立恢复；演练完整迁移执行器，记录耗时、锁等待、磁盘和WAL增长。
2. 维护窗口内停止所有资金写入：API请求、批量任务、后台实例、支付履约/回调重试与人工调额。先结清或核验冻结任务、待退款及未知结果退款，记录恢复计划；不丢弃支付通知。
3. 运行候选程序前设置 ACTIVITY_MAINTENANCE_CONFIRMED=1，仅作为已排空写入的人工确认。257/259/262在有用户的库中否则拒绝执行；5秒锁超时需排查长事务后重试，不能靠无限延长掩盖问题。上线后移除该变量。
4. 校验余额与来源总额、冻结余额与来源占用。259把历史余额归待确认，不可全部冒认本金；按充值/赠额证据逐户核验。待确认金额可以消费，但不计活动有效消费且不能普通本金退款。

## 启用

使用libpq环境 PGHOST、PGPORT、PGUSER、PGDATABASE（数据库名，非URI），凭据通过.pgpass或受控环境注入。脚本要求显式PGHOST，避免误连默认本地库。不要将密码写进命令行或提交仓库。

```bash
scripts/activity-rewards-control.sh status
export ACTIVITY_OPERATOR_ID=123  # 实际负责的管理员ID
scripts/activity-rewards-control.sh enable-processing
# 观察健康接口、积压与对账，确认后台处理正常后：
scripts/activity-rewards-control.sh enable-awards
```

脚本在事务内记录操作者及动作；enable-awards检查来源总额、冻结来源及处理开关。这是当前快照检查，不能代替维护对账或保证后续数据永久正确。确认活动预算、个人上限、签到月上限与历史待确认策略，再小预算灰度。用户ID分组不隔离全局数据库迁移。

GET /api/v1/admin/activity/health 返回处理/发奖开关、积压数、失败/等待数、最早待处理时间、最近成功与错误。建议以持续积压增长、最早事件超过60秒、连续处理错误告警为起点，再根据演练调整；这些不是已测得SLA。预算不足或退款审核也会产生等待，需结合具体错误判断。事件最长退避300秒，领取截止前仍未处理的事件不会越过截止补发。

## 紧急处理与恢复

```bash
scripts/activity-rewards-control.sh stop-awards
scripts/activity-rewards-control.sh stop-processing
scripts/activity-rewards-control.sh status
```

停奖等待正在持共享锁的领取事务结束后提交；停止处理允许已读取开关的任务完成，单轮有5秒上下文限制。停止后仍记录消费来源和可靠事件，充值、消费和退款依赖新的资金函数。恢复时先enable-processing，核验积压和预算，再enable-awards；已确认事件不会重复预留。

退款调用前保存本金占用；调用超时、断连或提交后崩溃均按结果未知处理，查询原支付方确认，禁止自动重发或直接返还资金。若崩溃发生在网关调用前，提供方可能查无记录，也须人工核验后决定取消占用或重试，不凭一次查询失败自动补退。存量历史REFUND_PENDING/ROLLBACK_FAILED需单独核验，不能认为新证据可自动补全旧订单。

禁止直接运行旧二进制回滚：旧程序不携带新来源上下文，数据库触发器仍存在。优先停奖/停计算并前向修复；资金触发器故障须进入资金维护窗口，核验后修复。不得盲目禁用触发器、删表或用旧备份覆盖上线后交易。恢复旧备份仅用于隔离灾备实例，恢复生产必须处理备份后的交易和支付对账。

## 必须留存的验收证据

完整schema升级和重复启动、峰值并发扣费延迟/吞吐、长事务锁等待、队列追平速度、支付成功/失败/未知结果与回调、批量任务来源保全、停奖/停任务/服务崩溃恢复、备份恢复及交易补偿。当前本地合成数据测试不覆盖真实规模与提供方行为，完成这些项目之前保持开发验收状态。
