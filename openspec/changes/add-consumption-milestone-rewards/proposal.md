# 消费阶梯奖励设计方案

状态：已完成本地实施，活动保持未发布；实际行为与初稿差异见 implementation.md。此方案取代上一轮二次充值试验的新增发奖设计，已有奖励与审计记录保留。签到继续独立运营，其资格门槛仍使用当前可配置规则。

## 1. 目标与定位

目标是提高用户持续使用 API 的频率、消费周数和消费留存，而不是增加充值笔数或签到次数。签到负责回访，消费阶梯负责把回访转化为实际使用。首期不增加抽奖、补签或付费解锁奖励。

首期做全站统一的一期 30 天活动，使用北京时间明确开始、结束时间，以服务端时间为准；不是每位用户独立滚动 30 天，不自动按月重复。期间加入的用户享有同一截止时间。活动开启前的消费不追溯；新老正常账户均可参与，沿用稳定分组做对照，不把全部历史用户消费一次性转换成奖励。

## 2. 三档奖励与成本

以下是试验候选值，尚未写入配置或启用；上线前必须结合消费分布、各渠道成本、现有充值优惠和签到成本确认。

| 本期有效消费累计达到 | 本档额外奖励 | 全部达标且领取后的累计奖励 |
| --- | --- | --- |
| $10 | $0.30 | $0.30 |
| $50 | $1.20 | $1.50 |
| $100 | $2.50 | $4.00 |

每档独立发奖，每人每期每档一次；进度不会因领取归零。直接消费到 $100 的用户可以领取全部三档，共 $4，不要求先领第一档才能继续累计。卡片必须标注“本档奖励”，避免把 $2.50 误读为累计返还。

本组示例在各档达标点的累计面值回馈约为 3%、3%、4%，不保证产生同等增量消费。站点当前 ¥1 充值得到 $1 余额，因此奖励 $4 按可售额度面值相当于 ¥4，不能按市场汇率低估成本。实际成本还取决于奖励使用率、渠道与模型成本。

金额阈值按近期用户有效消费分布再校准：第一档让轻度真实使用者有机会到达，第二档覆盖持续使用者，第三档覆盖较高消费者。如果大多数用户在第 1 天完成全部档位，或几乎无人达到第一档，应调整下一期，而非活动中途移动门槛。

## 3. 什么算有效消费

仅累计本期内已确认扣款、由用户真实付费本金支付的普通 API 使用金额，以用户最终实际扣款计算，不使用模型标价或渠道上游成本。

- 排除赠送余额、签到奖励、阶梯奖励、充值赠金、邀请奖励、注册赠额、免费调用、Cyber 请求、订阅额度消耗和被撤销的费用。
- 充值、转入余额、兑换码及人工调额本身不增加消费进度。兑换码或人工入账只有具备可核验的真实付费来源时，才能归为本金；否则归为赠送或待确认来源。
- API 同一笔扣款不能因用量补写或请求重试重复累计。不能单凭 usage_logs.actual_cost>0 宣称请求成功；以最终结算扣款记录作为依据。
- 合法计费失败也可能产生上游成本，是否计入以站点最终向用户收取且未冲正的结算金额为准，不使用前端 HTTP 状态判断。
- 有效消费保留与账务一致的 8 位小数，不逐条四舍五入到美分；阈值与奖励由美元输入，奖励最小 $0.01。展示不得把未达标进度向上舍入成已达标。

例如一笔扣款 $2 中赠额支付 $0.80、本金支付 $1.20，只增加 $1.20 活动进度。奖励赠额优先使用；其使用不再次增加进度。用户账户余额展示为总可用额度，同时可以展开查看本金与赠额。

### 已确认的账务前置条件

当前 users.balance 是统一余额，activity_reward_ledger 只记录发奖，不记录每笔消费使用了本金还是赠额。因此现有 actual_cost 汇总不能实现上述口径。必须先完成资金来源台账与扣费分摊，不能用“总消费减总奖励”的估算冒充本金消费。

历史余额需要对账后确定本金与赠额的期初分配，无法确认的部分列为待确认资金并不计入消费奖励。不得直接把全部历史余额归为本金；不得从用户可用总余额中删除待确认资金。上线前应提供管理员对账、确认和纠错工具，并向受影响用户解释计入口径。

## 4. 用户页面

保持现有仪表盘骨架，在消费统计附近放一张独立卡片；顶栏签到入口保留，不为消费奖励新增大弹窗或自动弹出营销层。

桌面结构：

```text
消费阶梯奖励   本期有效消费 $30.50       再消费 $19.50，可领取本档 $1.20   活动规则

  ✓ 第1档                      ◉ 第2档                      🔒 第3档
  满 $10，奖励 $0.30             满 $50，奖励 $1.20             满 $100，奖励 $2.50
  已领取                        进行中                        未达标

本期：11/20 00:00—12/20 00:00（北京时间）       已领 $0.30 / 本期最多 $4.00
仅计入本金支付的实际 API 消费；赠额消费不计入。                   查看奖励记录
```

日期仅为布局示例，正式页面完全读取活动配置。三档等距布局，连线按当前两个相邻阈值间的完成比例填充，标明真实金额，不暗示 $10/$50/$100 是等额间距。数值来自服务端，不能靠动画推算资格。

移动端改为三行阶段列表，每行显示阈值、奖励和状态；顶部突出下一档差额，避免压缩为不可点的小节点。浅色、深色、键盘焦点与读屏文本沿用项目组件规范。

### 状态与文案

| 状态 | 页面行为 |
| --- | --- |
| 未开始 | 显示开始日期，不能领取 |
| 进行中未达第一档 | 显示距第一档差额和活动截止时间 |
| 已达标待领取 | 对应节点显示“领取 $X”，同时显示待领总额；提供“领取全部” |
| 多档已达标 | 每档均可独立领取，领取全部使用同一事务，按档位顺序处理 |
| 全部领取 | 显示“本期奖励已全部领取”，继续保留记录 |
| 结束后领取期 | 消费不再累计，保留已达标奖励领取入口及领取截止日期 |
| 领取期结束 | 未领取资格过期；已发奖励不撤回 |
| 暂停 | 展示暂停原因，暂停新进度与新资格，保留此前已预留的奖励领取能力 |
| 未进入试验组 | 不出现可领取的营销卡；历史记录仍可查 |
| 费用冲正/退款审核 | 明确展示进度调整或待审核原因，不显示笼统“操作失败” |

阶段奖励达标后手动领取，可一次领完已达标档位；请求处理中禁用重复提交，超时重试不得重复发钱。领取成功更新总余额、分项余额和奖励记录；以服务端为准。

## 5. 时间、规则与奖励有效期

消费累计区间为 [开始时间, 结束时间)，按结算发生时间归属，迟到数据设 24 小时结算宽限，宽限内不计结束后的新消费。领取截至活动结束后第 7 天；宽限应在领取截止前结束。达标与领取截止由服务端裁定。

首期领取后的奖励无额外到期时间，仅用于站内 API，不提现、不作为本金退款。若要“活动赠额 30 天后失效”，需要独立额度批次及到期扣减、消费分摊和退款处理；明确列为后续能力，不在第一期界面做虚假承诺。

活动发布后冻结时间、阈值、奖励、统计口径及分组。后台允许暂停，允许提高预算与限额；降低预算不得侵占已预留金额。改金额或期限创建下一期，不修改已达标用户权益。

## 6. 预算与公平性

活动采用可配置的稳定参与比例，默认关闭。总预算按“已预留待领取 + 已发放”占用；单用户上限也包括待领预留额，不以页面点击先后抢占预算。

活动本期预算、共用活动累计预算、单用户活动累计上限三者同时有效。每期个人奖励上限为三档之和（例 $4），不得通过配置更低上限导致已承诺档位无法领全；后台启用前校验预算与限额，明确签到也消耗共用限额。

首次达标时原子创建资格并预留完整本档奖励；不做部分发放。预算不足时暂停产生新资格并清楚显示原因；运营应在接近阈值时预警和补充预算。不得让用户显示“可领 $X”后点击才告知额度耗尽。未领取资格到期后释放预留额；已发奖励永久计入支出。

为减少中途预算不足，发布前按预计参与人数、达档率测算；极端承诺上限为参与人数 × 每人全部档位奖励之和。若不能覆盖极端值，应明确活动总预算和预算耗尽规则，持续监控，必要时关闭新增参与。

## 7. 退款、冲正与异常

本金充值退款只退可核验、未消耗且可退的本金，不退赠额；已经正常消费的本金不因申请退款直接从活动进度中扣除。发生消费扣费冲正时，按原请求精确冲减有效消费。

冲正使未领档位低于阈值时，撤销该资格并释放预留；已领奖的情况转人工审计，暂停该用户新的消费奖励领取，不自动从本金强扣，不删除历史流水。拒付、异常退款及人工纠错也进入同一审计流程。是否补发、扣回赠额需显式记录处理人与原因。

所有资格判定均检查用户状态。限制活动领取接口频率、独立审计多账户行为，不能把频繁合法调用当成作弊。

## 8. 管理配置

替换当前二充卡片的运营入口为“消费阶梯奖励”，保留签到卡片和共用预算区。旧二充字段与已发记录保留只读/历史入口，不删除表或重写流水。切换发布时先关闭二充，避免两个方案意外叠加。

配置包括名称、开始/结束时间、领取截止时间、参与比例、三档美元门槛与奖励、本期预算、共用总预算与单用户累计上限；页内展示已预留、已领取、剩余预算、参与人数、达标人数、实际成本及审计待办。

发布前校验：阈值正数严格递增；奖励正数且最多两位小数；本期结束晚于开始；领取截止晚于结算宽限；预算足够覆盖单人全部档位；共用限额不能低于个人承诺奖励；账务分流、对账与期初来源确认已通过。所有启用/修改操作进入管理员审计。

必要帮助提示：金额单位、计入本金口径、零值不代表不限额、哪些额度不按月重置、三层预算关系、活动结束不等于奖励消失、退款审核路径。

## 9. 低侵入实施边界

活动规则、配置、进度与资格单独维护，现有 UI 只接卡片和后台配置；不修改全局 CSS、基础组件或插件协议。与上游保持独立提交和清晰接入点。

但“本金/赠额分摊”必然触及统一入账、扣费、缓存与退款链路，不能诚实地宣称纯插件或零核心改动。先梳理余额充值、充值优惠、签到、注册赠额、兑换码、邀请、人工调额、退款和全部扣费路径，再决定可复用的最小账务扩展。未完成前不得启用真金奖励。

建议数据模块（名称为逻辑设计，最终以仓库约束为准）：

- 资金来源台账：真实本金、赠额、待确认来源的入账与期初，关联来源 ID；统一余额仍是总可用额，不能复制出两套独立余额权威。
- 结算分摊流水：以现有结算事件唯一键关联本金/赠额实际扣款及冲正，精度保持 8 位；并发事务下防重复分摊。
- 活动及冻结档位：一期一个版本，开始/结束/领取截止、分组、预算与状态。
- 用户活动进度：仅由已确认结算流水增量汇总，可从流水重放校准。
- 档位资格与预留：唯一 (活动,用户,档位)，状态为预留/领取/过期/撤销/审核；额度预留和更新在同一事务。
- 奖励流水：复用活动审计体系，新增消费阶梯类型与活动/档位来源。奖励入账、资格转已领与预留转支出同事务，提交后失效余额缓存。

读取接口返回活动规则快照、有效消费、下一档差额、各档状态、可领总额及截止时间；领取接口只接档位 ID 或领取全部与幂等键，不接客户端奖励金额或进度。后台另提供预览、发布、暂停、预算、审计接口。命名在实现方案阶段沿用现有 /activity 路由风格。

## 10. 交付顺序与验收

1. 数据核验：近 30/60 天的真实本金消费分布、毛利、活跃周数；梳理账务来源和扣费路径，核实历史可回溯程度。
2. 账务前置：来源台账、期初对账、分摊、冲正、缓存一致性；不改变用户可用总余额，历史归类差异可审计。
3. 影子统计：先不展示奖励，验证有效消费与真实本金扣款对得上，确认新增链路不会重复计费或计进度。
4. 阶梯与预算：配置冻结、资格预留、幂等领取、过期、退款审核和预算预警。
5. 页面与后台：按本文状态表实现卡片、移动列表、记录及配置；关闭新二充发奖。
6. 小比例发布：观察至少完整一期及领取宽限后再决定扩大，避免只看开活动当周的短期上涨。

关键验收：赠额消费不推进；混合扣费只计本金部分；阈值刚好达到可领、差最小精度不可领；同时跨多档不漏奖；并发领取不重复；同时达标预算不超发；停止活动仍可领已预留奖励；过期释放预留；费用冲正不删除账务；日志晚到按结算时间处理；新活动不会重算旧奖励；本期预算与签到共享约束正确。

## 11. 效果评估与最终上线参数

主指标：分配到试验组的用户中，每周有真实本金 API 消费的比例、连续消费周数、30 天消费留存。辅助指标为有效消费额、活跃天数、达档/领取率；护栏为奖励与签到叠加后的净毛利、退款/拒付率、异常账户率、投诉率及预算占用。

使用稳定随机分组，并在分组前按历史活跃程度分层；签到策略在组间一致。按分配人群分析，不只比较领奖用户。启动前约定最小有业务意义提升和毛利底线，样本量依基线计算；样本不足不宣称活动有效。

最终启用前待定的是：基于消费分布验证的三档金额、站点可承受总预算与参与比例、账务对账结论。当前候选规则已足够用于页面预览和技术评审，但不得直接作为生产发奖授权。
