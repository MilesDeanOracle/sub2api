# 生产部署就绪审查

审查日期：2026-11-18；初审基线：f129088b。后续已完成下述代码加固；**仍须完成生产副本迁移、容量和恢复演练后才能发布**。

本次为代码与本地隔离 PostgreSQL 验证；未连接生产库，未检查真实数据规模、流量、备份或生产版本差异。功能完成与分支提交不代表已达到生产准入。

## 上线阻断项

### P0：历史余额退款可能只退现金、不扣站内余额

迁移 259 第 8 行把所有存量正余额放入 unverified。`activity_refund_deduct` 仅扣 principal；但 `ExecuteRefund` 第 319–324 行接受少扣/零扣结果，随后按原 `GatewayAmount` 调用退款提供方。原有预检查只看总余额，未验证可退款本金。

隔离库复现：迁移前用户 balance=100；迁移后 principal=0、unverified=100；调用 `activity_refund_deduct(uid,100)` 返回 0，balance 仍为100。结合真实退款调用路径，扣款不足不会阻止原金额现金退款。这不是已经在生产发生的损失，是确定的代码路径缺陷；本次未调用支付网关。

验收：非强制退款必须在外部退款前验证并冻结足额、来源正确的退款资金；不足时拒绝，强制操作必须显式授权并审计。覆盖历史余额、混合赠额、并发消费、退款失败返还、重复回调与服务崩溃重试的真实服务链路测试。不能用把历史全部归本金来掩盖赠额来源。

### P1：活动判断与全站预算锁进入 API 扣费事务

余额变动触发器同步调用 `activity_reserve_consumption`，该函数在判断是否达到奖励门槛前锁定唯一 activity_config 行，再汇总用户消费与奖励。不同用户本金消费因此争用同一行，即使该次消费尚未达标。后台保存配置还持该锁扫描所有用户及额度，进一步扩大等待。

隔离库复现：连接 A 锁 activity_config；连接 B 对另一个用户扣费 $0.01，设置300ms锁超时，余额扣费失败；错误堆栈位于 activity_track_funds → activity_reserve_consumption → activity_config FOR UPDATE。实际生产延迟/吞吐损失尚未测量，不能把此复现当成容量报告。

验收：将资金扣费与营销奖励计算的故障域隔离，例如同事务记录可靠结算事件，再异步幂等累计进度与原子预留预算；明确延迟、重试、事件时间与活动截止规则。若保留同步方案，须避免每笔消费锁全局行，并通过生产规模压测证明容量。

### P1：迁移不是已验证的在线无损升级

迁移 259 在同一事务内为全量用户建立资金账户和期初流水，新增外键/触发器。隔离库在执行到建用户跟踪触发器之前，已有外键持有 users 的 ShareRowExclusiveLock；并发 UPDATE users.balance 因锁等待超时。迁移提交前相关写入可能阻塞。实际阻塞时间取决于用户量、磁盘及并发事务，尚未在生产副本演练。

验收：在脱敏生产副本上演练真实迁移执行器，测量锁等待、耗时、WAL、磁盘、资金对账和应用启动；采用经确认的维护窗口或拆分为可恢复的分批回填与明确切换点。修改迁移策略时不得重写已应用的257–261校验和，应制定兼容已有测试环境的升级路径。

### P1：关闭活动不恢复原扣费路径，缺少验证过的紧急退回方案

活动关闭只控制发奖。余额变动资金触发器仍对所有用户写入台账；退款仓库也直接依赖新函数。隔离库验证两个活动开关均false时，一次普通余额扣减仍新增活动资金流水。因此仅关闭签到/暂停消费活动不能隔离账务触发器风险。回退旧二进制也不会移除数据库触发器，旧代码未携带来源上下文时还可能改变新资金分类。

验收：设计停奖、停奖励计算、保留资金账务、版本回退的分层操作与兼容矩阵；演练故障时继续正常充值/扣费/退款，保留已发与已预留奖励证据。不可直接删除资金表、盲目停触发器或恢复旧备份覆盖上线后的交易。

## 已有保护与验证边界

已有事务、用户锁、唯一奖励键、预算预留、8位消费精度、连续签到与月上限保护。重新执行 `TestConsumptionPostgres` 的8个场景通过，包含12路并发领取、资金来源、混合扣费、赠金、Cyber排除、批量冻结/捕获/释放、舍入边界、截止与发布冻结。测试使用独立本地 PostgreSQL 临时实例；均非生产库。

现有测试表结构为最小合成表，不能替代完整生产schema、真实支付服务、混合版本部署、存量退款/冻结任务、大规模负载与灾备演练。此前常规测试运行未配置ACTIVITY_TEST_DSN时，此PostgreSQL用例会跳过。

## 建议落地顺序

1. 修复退款资金冻结与外部退款金额的一致性，补真实服务链路回归。
2. 隔离奖励处理与主扣费链路，补持久事件、幂等、重试及预算并发验证。
3. 完成历史资金策略与生产规模迁移/对账演练。
4. 完成开关、指标、告警、回退与故障演练；冻结生产兼容矩阵。
5. 通过后先小范围、低预算灰度，逐步放量；不是仅按用户ID覆盖率就隔离了全局数据库改动。

当前分支保留在开发验收阶段。上述项关闭前，不建议合并为生产发布版本。

## 加固复核（2026-11-18）

- 退款：余额订单在调用提供方前，同一事务保存订单占用、足额已确认本金扣减及恢复证据；非强制退款拒绝零扣/少扣，事务回滚部分扣减。网络结果不明保留 REFUND_PENDING 与资金占用，只允许查询原退款，不自动重发。明确失败原事务返还；历史退款占用异常转人工核验。强制退款保留既有显式授权语义。
- 奖励：新增前向迁移262，结算事务只记录来源台账和持久outbox；后台任务执行活动计算和预算预留，预留与事件确认同事务提交，多实例使用 SKIP LOCKED。失败持久记录并退避重试；依据原结算时间判断活动归属，领取截止仍按当前时间。暂停后处理此前有效事件，暂停期间消费不回算。
- 维护：既有用户的257/259/262迁移要求 ACTIVITY_MAINTENANCE_CONFIRMED=1，设置5秒锁等待上限；不修改已应用的257–261。该变量是人工维护确认，不会自动停止写入。
- 控制：默认停处理、停发奖；新增健康接口及带审计的分层操作脚本。停奖不删除来源账务，也不恢复旧扣费实现。
- 验证：隔离 PostgreSQL 12个场景通过，含锁住共用预算时消费仍成功、任务异常不回滚消费、退避恢复、并发预留、暂停事件时间；带 unit 标签的退款/活动/结算测试通过，迁移维护与Wire清理测试通过。前端构建及真实组件模拟数据的桌面/移动/深色检查通过。

剩余准入项：生产完整schema与真实规模迁移、支付提供方沙箱/回调与崩溃恢复演练、历史本金来源和冻结任务核验、容量及备份恢复验证。当前测试使用合成表，不能替代这些验收。来源台账/触发器及outbox仍在资金事务内；异步隔离仅移除了营销计算和共用预算锁，不保证资金触发器故障时扣费可用。后台任务仍存在汇总查询，吞吐尚未得到生产规模证明。

发布与故障操作见 [production-rollout.md](production-rollout.md)。

## 指定用户测试保护

新增263及双活动独立开放范围，默认指定用户空名单。范围同时覆盖状态查询、签到、领奖和异步预留，范围变更记录审计；原始资金账务不受白名单影响。新增隔离 PostgreSQL 两个场景，合计14个场景通过；包含默认隐藏、无效用户拒绝、双活动隔离、范围外消费不预留、移除账号后拒绝直接领取且保留原预留，以及全量切换。前端新增4个开放范围测试，联合已有金额/进度测试14项通过。必须先排空不支持范围校验的旧实例，白名单无法弥补混合旧版本的访问控制缺口，也不能替代正式部署前的迁移和容量演练。
