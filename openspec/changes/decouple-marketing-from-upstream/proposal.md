# 降低营销功能的上游更新维护成本

## 目标

将“上游更新不用维护营销”作为可执行的工程目标，而不是要求营销与 Sub2API
成为两个独立部署的微服务。

普通上游更新应当在合并后直接通过，不修改营销业务代码。只有认证、计费、支付、
用户表结构等核心契约发生实质变化时，才需要维护少量适配代码和回归测试。

## 范围

- 营销领域代码、数据库对象、管理页面和用户组件保持专属命名与局部样式。
- Sub2API 对营销功能只暴露少量、可审计的集成位置。
- 核心计费、奖励钱包、退款仍保持同一数据库事务，不通过消息最终一致性替代资金原子性。
- 每次合并上游后运行固定的营销升级门禁。

## 非目标

- 不在本阶段拆成独立服务或独立数据库。
- 不承诺上游任意改动都零人工处理。
- 不重写已发布的迁移，也不删除历史活动数据。

## 验收

1. 路由和活动迁移兼容逻辑不散落在上游公共文件中。
2. 普通上游合并只需解决 `wire_gen.go` 等生成文件冲突并运行营销升级门禁。
3. 资金、退款、余额写入接口变化时，适配范围可定位到明确的适配文件。
4. `make test-marketing-upstream` 覆盖奖励领取、签到、抽奖、钱包转入、退款状态、匿名授权、后台开关和迁移路径。
