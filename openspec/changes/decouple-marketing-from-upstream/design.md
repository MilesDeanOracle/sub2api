# 营销模块与上游集成设计

## 形态

采用模块化单体，而不是远程微服务。营销模块与 Sub2API 共用进程和数据库，但将业务
实现、路由注册、迁移兼容和资金适配分开。这样保留现有资金事务的原子性，同时减少
上游文件的文本冲突和变更影响范围。

## 稳定接缝

| 接缝 | 责任 | 上游变化时的处理 |
| --- | --- | --- |
| `repository/activitystore` | 营销账务写入、用户余额调整、钱包锁 | 核心表或事务契约变化时，只改这里及对应测试 |
| `server/routes/activity_routes.go` | 用户和管理员活动路由 | 认证/中间件签名变化时集中适配 |
| `repository/activity_migrations.go` | 活动历史迁移兼容和维护窗口检查 | 迁移编号或历史兼容规则变化时集中处理 |
| `service/payment_activity_refund.go` | 余额退款与活动资金一致性 | 支付退款契约变化时集中适配 |
| 计费仓库中的活动事件写入 | 消费和图片预占来源事件 | 计费命令发生变化时补最小适配并跑财务回归 |

营销服务和组件不得新增对上游 Ent schema 的修改。读取 `users`、`usage_logs`、
`payment_orders` 时必须把表结构假设限制在明确的适配实现中。

## 上游补丁区

允许保留的公共文件改动应尽量只有以下类型：

- 路由文件中的一次 `registerActivity*Routes` 调用。
- Wire 依赖和生成文件中的一次活动服务注入。
- 计费、退款调用路径中的少量显式适配钩子。
- 用户概览和运营台中的单行组件挂载。

具体业务规则、SQL 主体和页面实现继续放在活动专属文件。合并上游时优先保留上游
结构，再把活动钩子接回这些稳定接缝。

## 资金约束

奖励钱包转入、退款回收、欠额偿还和抽奖发奖必须与核心余额更新处于同一事务。
不得为了减少冲突改成跨服务异步调用。营销适配层可以使用核心事务对象，但不得把
活动业务判断下沉到 Ent schema 或数据库触发器。

## 分阶段

1. 集中路由和迁移兼容逻辑，建立升级门禁。
2. 将剩余核心表读取逐步收入活动适配层，减少业务文件直接依赖核心 schema。
3. 只有独立发布和独立扩容成为真实需求时，才评估独立进程；届时重新设计账本接口
   与跨服务一致性策略。
