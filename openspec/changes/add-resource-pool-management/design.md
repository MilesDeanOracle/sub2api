## Context

当前账号与分组分别由 `AccountsView.vue` 和 `GroupsView.vue` 承载，两者已经通过 `group_ids`、`account_groups` 和筛选 API 形成多对多关系。账号页具备成熟的账号列表、批量编辑和账号弹窗；分组页则包含大量平台相关配置与高级路由/定价能力。两个页面体量都较大，直接拼接会进一步放大耦合。

管理端已引入 Element Plus，并已有 Element 风格的 Dashboard、Users 页面和公共组件模式，可作为新工作台的视觉与交互基线。现有后端账号列表支持按分组筛选以及 `ungrouped` 查询，账号创建/更新支持 `group_ids`，因此第一阶段可以复用既有 API 和数据模型。

## Goals / Non-Goals

**Goals:**

- 建立以分组为上下文的统一日常运维入口。
- 复用现有账号表格、账号弹窗和分组完整编辑能力，避免复制平台特有表单。
- 用 Element Plus 提供一致、响应式且可渐进演进的管理体验。
- 保持旧链接和既有业务语义兼容。

**Non-Goals:**

- 不合并账号与分组数据表，也不把账号改为只能属于一个分组。
- 第一阶段不重写 `GroupsView.vue` 中全部高级配置为 Element Plus。
- 不删除既有账号/分组 API，不改变调度、计费或绑定关系语义。
- 不把渠道管理、代理管理等其他资源纳入本工作台。
- 不在当前实例中导入、复制或持久化上游分组与上游管理员凭据。

## Decisions

### 1. 新增独立资源池工作台，复用而非拼接旧页面

新增 `ResourcePoolsViewElement.vue` 作为编排层，拆分资源池导航、摘要、账号表格和关系操作组件。旧页面继续作为复杂编辑能力与兼容入口存在。

选择这一方案是因为 `GroupsView.vue` 约 6900 行且包含大量平台特有配置，`AccountsView.vue` 也包含复杂的用量和批量操作。直接嵌套或合并会造成重复请求、弹窗状态冲突和难以测试的巨型组件。

替代方案“侧边栏折叠父菜单但仍跳转两个页面”改动小，却不能解决连续维护中的上下文丢失，因此不采用。

### 2. 路由状态作为工作台上下文来源

统一路由使用 `/admin/resource-pools`，以查询参数表达视图：

- `scope=all`：全部账号；
- `scope=ungrouped`：未分组账号；
- `group_id=<id>`：真实分组；
- 可选 `panel=group-settings`：从旧分组路由迁移来的配置上下文。

选择路由状态可以支持刷新、分享链接、浏览器前进后退以及旧路由重定向。组件内部仍可缓存筛选条件，但选中的资源池必须以 URL 为准。

### 3. 旧路由兼容重定向

`/admin/accounts` 重定向到 `/admin/resource-pools?scope=all`；`/admin/groups` 重定向到 `/admin/resource-pools?scope=groups`。带有明确分组 ID 的站内链接应转换为 `group_id`。旧页面保留一个不在菜单展示的内部路由，供高级分组配置或回退使用。

为了避免一次性重写分组高级配置，工作台的“高级配置”可以打开既有分组编辑路由/页面，并通过返回地址恢复工作台上下文。

### 4. Element Plus 组件边界

- `ResourcePoolNavigatorElement`：`ElMenu`/`ElScrollbar`、平台分组、计数和搜索。
- `ResourcePoolSummaryElement`：`ElCard`、状态/可用性统计和分组快捷操作。
- `ResourcePoolAccountsElement`：`ElTable`、分页、筛选、选择和账号常用操作。
- `AssignAccountsToGroupDialogElement`：`ElDialog` + 可分页/检索的账号选择。
- 分组创建采用轻量 Element 表单；完整编辑复用既有能力。
- 账号创建/编辑第一阶段复用已有弹窗，同时通过默认 `group_ids` 传入当前分组；后续可独立迁移为 Element 组件。

这样可以保证新页面整体为 Element 风格，又避免复制复杂的账号认证表单。

### 5. 关系更新优先复用账号批量更新

加入当前分组时，需要在账号已有 `group_ids` 基础上做集合并集；移出时做差集，绝不能用当前分组覆盖全部关系。前端应先获得选中账号的完整分组 ID，再调用现有单账号或批量更新 API。

若现有批量接口只支持“统一替换全部分组”，第一阶段逐账号提交并限制并发；只有性能验证表明不可接受时才新增专用关系 API。该选择降低后端变更和权限风险。

组内 `AccountGroup.priority` 若当前无可写 API，则第一阶段在 UI 中只展示；实现任务必须先确认现有端点。若不存在，补充最小的关系更新端点及权限/缓存失效逻辑，不能误用账号全局 `priority`。

### 6. 数据加载与缓存

分组导航加载轻量分组列表；右侧账号列表使用服务端分页和 `group` 筛选。选择分组时不预加载所有账号。分组摘要优先使用分组列表已返回的 `account_count`、`active_account_count` 和 `rate_limited_account_count`。

创建、绑定、解绑或编辑成功后，只失效当前账号列表、受影响分组计数和全部/未分组计数，避免整页刷新。

### 7. 上游账号管理使用服务端临时探测

资源池页工具栏新增“上游账号管理”，使用 `ElDrawer` 从右侧展开，桌面宽度为视口的 50%；窄屏下采用可用宽度以保证表单与表格可操作。抽屉内部使用 `ElForm` 收集 Base URL 和管理员 API Key，探测成功后使用 `ElTable` 展示上游分组。

浏览器不直接访问上游，避免 CORS 限制，也避免把上游 API Key 交给不受控的前端重定向链。新增当前实例的管理员探测端点，接收一次性的 Base URL 与 API Key，在服务端规范化 Base URL 后使用 Bearer 凭据请求兼容的 `GET /api/v1/keys`，遍历分页并对各 Key 的 `group` 按 ID 去重。请求必须设置超时、限制响应体、拒绝 URL 用户信息与非 HTTP(S) 协议，并禁止跟随到不同源的重定向；响应只投影表格需要的分组字段，不返回或记录 API Key。

探测状态只保存在抽屉组件内；关闭抽屉时清空 API Key、结果和错误，不写入 localStorage、sessionStorage、数据库或运行时设置。Base URL 也不持久化，确保该能力是只读检查工具而非上游配置管理。

## Risks / Trade-offs

- [旧分组高级配置仍是非 Element 页面，视觉存在跳变] → 通过工作台抽屉入口和明确返回上下文降低割裂，后续逐步迁移。
- [复用账号更新接口可能造成 N 次请求] → 第一阶段限制并发并提供进度/失败汇总；必要时再增加专用批量绑定 API。
- [账号列表轻量响应可能不包含完整分组关系] → 对关系操作使用完整账号详情或专门的数据接口，不能基于截断展示数据更新。
- [旧站内链接大量指向 `/admin/groups`] → 路由层统一重定向，并搜索修正需要保留具体上下文的链接。
- [分组多平台和 Composite 规则复杂] → 导航允许展示所有分组，但绑定操作沿用服务端平台兼容校验及混合通道风险确认。
- [新旧页面同时存在易产生重复实现] → 工作台只承载日常编排，复杂编辑继续单一来源；公共逻辑提取到 composable/API 层。
- [管理员可输入任意上游 URL，存在 SSRF 与重定向泄露风险] → 仅允许 HTTP(S)、复用出站安全校验、设置严格超时和响应上限，并禁止跨源重定向携带凭据。
- [不同版本的 Sub2API 分组响应字段可能略有差异] → 后端验证标准响应包络并只投影稳定字段；响应不兼容时返回明确错误而不猜测数据。

## Migration Plan

1. 先添加新路由、页面和组件，不修改旧菜单入口，便于开发验证。
2. 完成账号筛选、分组选择、创建和绑定/解绑关键流程测试。
3. 将侧边栏两个入口替换为“资源池管理”，同时配置旧路由重定向。
4. 更新 Dashboard、引导文案及所有站内硬编码链接。
5. 上线后保留内部旧视图路由至少一个版本；若出现阻断问题，可回滚菜单和重定向而不涉及数据迁移。
